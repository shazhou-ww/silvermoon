# 调研并优化 pnpm check 性能回归

## 意图

解释当前 `pnpm check` 再次变慢的原因，建立与历史已验收基线可比较的新证据，并在
不减少任何发布级验证覆盖的前提下实施有针对性的第二阶段优化。

## 背景

已完成的 `faster-test-suite` idea 曾在 Node.js 24.12.0、pnpm 11.22.0 环境中，
把预热后五次 `pnpm check` 的中位耗时从 54,585ms 降到 32,773ms，并保留 unit、
contract、integration、e2e、package、Markdown 和 skill 六类门禁。其主要手段是
并行执行独立发布检查，并已证明调度器失败汇总和测试隔离有效。

随着 CLI、idea lifecycle、发布验证、installed-package E2E 和其他回归覆盖继续增长，
当前开发体验再次表现为 `pnpm check` 非常慢。尚不清楚主要原因是必要测试数量增长、
关键路径中的重复安装与打包、integration fixture 的 Git 子进程、网络相关 smoke、
调度器资源竞争、冷暖缓存差异，还是某项新检查落入了不合适的完整门禁。

在重新测量前直接设定固定优化百分比可能把环境波动或自然测试增长误判为回归，也
可能诱导为达成数字而弱化覆盖。因此本 idea 先调研并形成可复现基线，再依据关键
路径证据确定优化目标。

## 期望结果

- 在固定工具版本与受控机器状态下，分别记录当前 `pnpm check`、各并发门禁和关键
  子阶段的预热后多次耗时、离散情况、测试数量、子进程及外部 I/O。
- 把当前结果与 `faster-test-suite` 的已验收本地基线和适用提交进行可解释比较，
  区分真实性能回归、覆盖增长、环境差异和测量噪声。
- 在修改优化代码前，基于调研证据写下可测量的目标、所针对的关键路径及不能牺牲的
  覆盖；目标不预先固定为任意百分比。
- 实施与证据对应的优化，使相同环境下的关键路径和完整检查达到事先记录的目标，
  并保留全部现有测试、发布门禁、失败诊断和隔离保证。
- 开发者可以看到各门禁耗时与完整墙钟，未来能判断变慢来自新增覆盖还是意外回归，
  而不是只能依赖主观体感。

## 范围

### 范围内

- 复现并复核历史 `faster-test-suite` 基线方法，建立当前完整与分层耗时基线。
- 分析 `scripts/run-checks.mjs` 的并发关键路径、CPU/磁盘竞争、重复命令和失败汇总。
- 分析 integration fixture、真实 Git 子进程、package pack/install、installed-package
  E2E、skill discovery 和 Markdown 检查中的高成本操作。
- 在调研证据后选择并记录性能目标，再优化重复准备、缓存边界、测试 fixture、进程
  调度或门禁分层；所有必需发布验证仍由 `pnpm check` 覆盖。
- 为性能证据和明显回归建立轻量、跨平台、不过度依赖绝对机器速度的观察方式。
- 更新贡献者与 CI 文档，说明快速反馈入口、完整发布门禁和基准复现方法。

### 范围外

- 删除、跳过、弱化现有有效断言或把必需发布门禁移出 `pnpm check`。
- 预先承诺未经测量支持的固定百分比、固定毫秒预算或单次运行结果。
- 仅因测试暴露瓶颈而改变用户可见 CLI、schema、生命周期或发布语义。
- 依赖特定开发者机器、付费基准服务或常驻 daemon 才能获得正确结果。
- 把外部网络波动、CI 排队时间或缓存偶然命中计为代码优化收益。
- 发布新的 npm package 版本；本 idea 只调研、修改并验证仓库内容，不执行 npm 发版。

## 约束

- 基线与优化后测量使用相同 checkout 条件、Node.js/pnpm 版本、机器电源状态和命令，
  包含预热并采用多次运行的中位数，同时保留原始样本。
- 性能目标必须在优化实现前根据基线与关键路径证据记录，完成后不能为迁就结果而
  静默降低；若证据变化，须显式修订合同和 ledger。
- `pnpm check` 继续等待并汇总全部并发门禁结果，不得让早期失败掩盖其他失败。
- 单文件、分层和完整套件保持独立可运行；测试不得依赖顺序、共享可变状态或遗留
  临时仓库、Git 配置、引用、环境变量和后台进程。
- 真实文件系统、Git、打包与安装行为继续由 integration/e2e 证明，不能全部替换为
  mock；新增测量本身不能显著拖慢普通检查。
- 保持 Node.js `>=22`、Windows 和现有 CI 平台兼容，不新增重量级性能依赖。
