# 设备级 daemon 与事件驱动的 Agent 协作

## 意图

让 Silvermoon 成为上游沟通者 Agent 与下游执行者 Agent 之间可持续交互的桥梁，
由确定性的 loop harness 推进工作，不再依赖一个 Agent 同时承担沟通和执行职责
时对循环策略的自觉遵守。

通过同一个 Silvermoon 包提供设备级 daemon 子命令，并让各项目使用自身版本的
Silvermoon 决定流程。以 idea 本地的 append-only JSONL 事件日志取代
`status.yaml`，使生命周期事实和交互进度都能从事件重建。本次工作以 `0.4.0`
及新的持久化 schema 版本为目标，不把记录本 idea 等同于批准实施或授权发布。

## 背景

当前 Silvermoon 作为无状态 CLI 提供观察与下一步建议。Agent 调用
`whats-next` 后自行决定如何继续，同时承担人与 Silvermoon 之间的沟通者、
循环调度者和具体工作的执行者。这些角色混在同一上下文中，使继续、等待、
求助和恢复的行为过度依赖 Agent 的临场判断。

期望的职责关系是：

```text
人 <-> 上游沟通者 Agent <-> Silvermoon daemon <-> 下游执行者 Agent
                                  |
                         项目版本 Silvermoon
```

上游理解人的意图、取得明确决策并提供新的指令；下游负责执行工作，并在无法
自行推进时求助；Silvermoon 提供规则化的推进和消息路由。这里的 daemon
协调是本机上下游 Agent 之间的执行交互，不是另造一套基于 primary 的跨设备
任务协调机制。

设计来自 2026-09-30 至 2026-10-01 的 daily discussion。关于上游打断的最终
决定是允许随时追加 `ping`，取代此前“必须先暂停、确认停止，再发新指令”的
方案；不得把旧方案重新作为轮次限制。

## 期望结果

### 一个包、一个设备级 daemon、独立的项目版本

用户从 Silvermoon 的子命令启动长驻 daemon，不需要安装另一套 daemon 产品
或独立命令。现有无状态 CLI 和 `whats-next` 仍可独立使用。

一台设备由一个 daemon 接收上游面向不同项目的工作，并路由到对应 idea 的
下游 Agent session，而不是要求每个项目维持一个常驻 daemon。

全局 daemon 与项目使用的 Silvermoon 通过进程隔离解耦。项目可以使用不同的
Silvermoon 版本和 schema，不要求同步升级，也不要求包版本彼此兼容。
双方依赖明确的进程间调度协议；无法交互时必须显式报告，不能用 daemon 的
项目解释逻辑替代项目版本。

项目对应版本的 Silvermoon 解释项目事实、归约事件，并决定正常流程应继续
执行还是交还上游。全局 daemon 根据结构化结果落实调度，管理 Agent session，
并处理进程崩溃、连接失效等运行故障，不维护另一套项目生命周期规则。

### 以一个 idea 为范围的可追加指令交互

每个 `ping` 绑定一个确定项目中的一个 idea，而不是隐式授权遍历项目中的
其他 idea 或执行跨项目的复合任务。一次工作最初由上游发出 `ping`。

`ping` 表示发起、恢复或补充执行指令。上游在下游运行中也可以追加新的
`ping`，不必等待 `pong`，不必先停止执行，也不受“当前不是自己的轮次”
的限制。新增指令交给该 idea 关联的下游 session，不因此另起同一 idea 的
并行执行者。

`pong` 表示将结果、问题或继续所需的输入交给上游，不等于完成、阶段性完成
或验收。下游认为当前 `next step` 无法自行推进、需要人介入时可以请求
`pong`，包括 sign-off、工作阻塞和 Git 提交失败。daemon 不能要求下游一定
达到预定里程碑才允许求助，也不能在下游进程失效时无限等待它自行返回。

上游处理问题后可以发送新方向，而不只是重试原指令。例如，Git 提交失败后，
上游可以要求暂缓提交，先调查 Git 问题；桥梁必须继续可用，允许把该指令
送达下游。暂缓提交不表示删除本地修改、丢弃历史或绕过人类决策。

事件能够关联交互请求、执行和响应，并区分已处理与尚未处理的指令。运行中
出现多个 `ping` 时，旧执行结果或 `pong` 不能误清除新指令、使其丢失，
也不能把收到消息自动视为已完成该消息要求的工作。

### 规则化推进与 session 连续性

取下一步、重新观察、继续执行以及向上游交还的循环由 Silvermoon 承担。
下游 Agent 做具体工作，不再独自承担完整的 `whats-next` 循环策略。
规则化循环允许明确求助和退出，不以无限重试代替错误处理。

同一 idea 的多轮交互尽量复用同一个下游 session，保留上下文；session 失效
时才重建，并明确恢复依据。第一版定义统一的 Agent 适配边界，至少内置
GitHub Copilot CLI 的启动、会话恢复和消息收发能力，而不是只交付协议、
要求使用者自行实现全部连接。

追加指令的接收、送达和处理边界必须可观察。适配器不支持执行中立即消费指令
时，不能把指令静默丢弃或错误宣称已生效；允许随时追加不意味着正在发生的
外部副作用能够瞬间撤销。

daemon 重启或连接恢复后，从事实恢复状态，不因回放事件而盲目重复执行动作。
不能仅因缺少完成记录，就假定之前的工作从未执行。

完整执行日志，包括 Agent 的完整对话、工具调用和逐步输出，由下游 Agent
负责。Silvermoon daemon 不承担这些日志的采集、存储或管理。

### 事件成为持久事实，status 成为投影

每个 idea 使用同级的 JSONL 文件保存版本化事件，取代 `status.yaml` 的
权威地位。新 schema 下不再维护第二份可独立编辑的权威 status；
状态缓存如存在，必须能够由事件重建。

日志包含重建生命周期和调度状态所需的事件、必要结果和证据引用，而不是
所有底层运行输出。生命周期投影与调度投影分别回答“哪些世界版本已被明确
认可”和“哪些指令正在执行、等待或已交还”，不得相互推导。

批准、验收、放弃及其显式更正只能由明确的人类决定形成对应事实。
涉及世界版本的决策事件包含被决定对象的准确 revision/hash；世界 revision
的变化或观察也进入归约所需的事件输入，使有效生命周期可以由事件重建。
旧版本的批准事实保留，但不自动适用于新版本。

`ping` 不是批准，`pong` 不是验收，下游报告完成也不是人类接受。新增交互
事件不能通过改变被审查世界的内容 revision 而使其自身触发失效。

常规事件写入通过项目对应版本的 Silvermoon 子命令完成，由该子命令校验并
追加。不能只提供供 Agent 直接调用的库接口，也不要求 Agent 手工编辑 JSONL。

`check` 能够检查相对于相应 Git 历史基线的 append-only 约束，拒绝删除、
重写既有事件或非法追加。错误的事实通过明确的新事件更正，而不是就地改写。
当前快照合法与历史追加合法是不同的检查责任，不能只凭文件可解析就宣称
满足 append-only。

### 本地响应与既有 Git 协作边界

交互以本地 idea 的 JSONL 为依据，不必等待 commit，更不必等待事件进入
primary 才能继续。合法的事件文件未提交追加不应独自触发干净工作区阻塞；
其他文件仍遵循相应的原有检查和保护规则。

即使 normal lifecycle 被 Git 问题阻塞，接收求助、追加新指令和执行明确的
诊断工作仍然可用。交互通道不能被要求先解决 Git 阻塞的前置条件锁死。
这不等于自动允许带着无关代码修改越过 lifecycle gate。

跨设备的事实共享、协调和合并继续通过 Git primary 完成，不增加分布式锁、
租约、中心协调服务或跨设备唯一执行权保证。本地已经执行不等于已经同步；
遇到并发历史必须保留双方事实并显式处理，不能静默重放过期决策。

### 显式的一次性迁移

选择升级的项目可通过独立的一次性入口，将旧 `status.yaml` 中的已知事实
导入新 JSONL，完成后不再保留旧文件作为权威状态。迁移入口不加入
Silvermoon 的常规主命令子命令集合，也不在普通启动时自动迁移。

迁移不得伪造旧事实原本未知的发生时间、操作者或事件顺序；应明确区分导入的
既有事实与升级后真实发生的事件。原有 idea 身份及仍然适用的元数据不得静默
丢失。迁移失败时必须保留可恢复的原始事实，重试不得产生重复决策。

## 范围

### 范围内

- Silvermoon 包内的设备级 daemon 子命令、确定性 harness 与上下游消息路由。
- 项目运行时的进程隔离、结构化调度协议和独立版本演进边界。
- 以单个 idea 为工作范围、运行中可追加 `ping` 的交互语义。
- 下游 session 复用、恢复和首个 GitHub Copilot CLI 适配器。
- 替代 `status.yaml` 的 JSONL 事件协议、状态归约与 schema 升级。
- 校验并追加事件的项目本地子命令及 append-only 历史检查。
- 本地未提交事件驱动交互、Git 阻塞下仍可求助和接收新指令的行为。
- 独立的一次性旧格式迁移入口。
- 与新行为一致的 CLI 帮助、文档、skill 和可观察的行为证明。
- 以 `0.4.0` 为目标的兼容性及交付准备；真实发布仍遵循独立的发布授权流程。

### 范围外

- 单独发布一个 daemon 产品，或强制每个项目启动一个常驻 daemon。
- 要求所有项目与全局 daemon 使用相同或相互兼容的 Silvermoon 包版本。
- 新的跨设备协调系统、分布式锁或独立于 Git primary 的共享事实权威。
- daemon 管理下游完整执行日志，或把模型 token、工具输出和心跳全部写入 Git。
- 严格交替的 `ping/pong` 轮次锁，以及新指令必须等待确认停止的前置限制。
- 由 Agent 或 daemon 自动批准、验收或放弃 idea。
- 第一版必须支持所有 Agent 产品、聊天 UI、操作系统服务安装器或可视化控制台。
- 本次记录工作直接实现 daemon、替换现有 schema、迁移现有 idea 或发布 npm。

## 约束

- 项目版本持有正常流程规则，全局 daemon 不得重新解释项目生命周期。
- 进程间协议兼容不等于 Silvermoon 包版本或项目 schema 必须兼容；
  协议不支持时必须给出明确错误。
- 追加事件的子命令须防止本机并发追加导致记录损坏或已接收指令丢失；
  不把该责任扩展成跨设备锁服务。
- 解析失败、部分写入、未知事件或无法确认的执行结果不得被静默跳过、
  冒充成功或自动转化为人类决策。
- 人类决策保持与准确世界 revision 绑定；同步和交互消息均不能替代决策。
- 保留未知修改和并发历史；不得依赖 force-push、reset、广泛 clean 或
  静默覆盖来完成恢复与迁移。
- 本 idea 在当前版本下仍使用现有 `status.yaml` 和 canonical 世界布局记录；
  目标格式只能在获准实施并交付升级后启用。

## 实施时需细化

产品方向已明确。以下是实施契约需要具体化并证明的细节，不代表重新开放以上
已确定的职责和行为边界：

- JSONL 文件名、事件 envelope、版本策略、身份和元数据的表示，以及世界
  revision 观察进入事件流的时机。
- 进程间协议与项目运行时发现方式，以及 Copilot CLI 对执行中追加指令、
  session 恢复的实际能力和适配行为。
- 多个 `ping` 与 `pong` 的关联、排序、送达确认、去重，以及重启后对
  “已执行但尚未记下结果”的恢复策略。
- 本地追加的完整性、历史基线选择和 Git 合并后事件归约的确定性。
- Git 阻塞诊断与正常 lifecycle 路由的分界，以及独立迁移入口的具体形式。
