# 从世界状态到专业导向：建模思路的推演

本文整理本次讨论的概念推演，解释为什么可以用状态分层来表达专业人士的工作导向，再由观察、问题与指导组成 Agent 的导航机制。它提供理论背景，不增加本 Idea 的实施范围；具体契约见[Objective Guidance 类型体系](./objective-guidance.md)。

## 1. 起点：我们要表达的不是一条 happy path

专业人士指导 Agent 时，常见做法是列出动作：先做 A，再做 B，最后做 C。这能描述一条正常路径，却不能充分回答：起点不同怎么办，动作失败怎么办，别人同时改变环境怎么办，什么时候才算完成？

我们希望积累的是一类专业问题的解决能力，而不是一个案例的操作记录。因此先改变建模对象：

> 不先规定完整行动路径，而先规定世界应当朝什么状态推进，以及怎样判断当前的位置。

Happy path 仍然有用，但只是这个导向下的一条可能路径。

## 2. 世界状态是什么

世界状态是与当前工作有关的现实状况，不只是一个文件快照。它至少包含：

| 维度 | 示例 |
| --- | --- |
| 物质与运行事实 | 代码、设备、测试结果、服务、订单、交付物 |
| 规范与决定事实 | 权限、承诺、人工接受、约定标准 |
| 信息与认知事实 | 已取得的证据、尚未知的信息、双方已沟通的内容 |
| 时间与历史关系 | 哪个版本被验证或接受、事实是否仍然有效 |

例如，两份代码即使完全相同，一份已被验证并针对精确版本接受，另一份没有，它们在工作推进中的状态也不同。

这里的“世界”不是要求程序穷尽整个宇宙，而是概念上承认：影响工作成立与否的事实可能分散在文件、远端系统、人和交互历史中。

观察对象则用于限定本次工作，例如某个项目和 Idea ID。对象不是世界状态的完整输入；观察一个 Idea，也可能需要查询它所在的项目、设备与远端仓库。

## 3. 如何把世界状态定义成标量场

选定工作对象和目标后，专业人士定义一组有序层级：

```text
0 < 1 < 2 < ... < N
```

并为每层给出判定条件，把相关世界状态分类到其中一层：

```text
level(世界状态) -> 一个非负整数层级
```

这就是将高维状态投影到有限全序集。可以把它想象成梯田：

- 一层包含很多不同的具体状态，具有相同的层级值；
- 跨过判据规定的边界，才能进入上一层；
- 最高层级唯一，但满足最高层级的具体状态可以有多个；
- 层级表达顺序，不表达等距的收益、工作量或难度。

这种场是离散、分片常量的，不需要假设世界具有连续坐标，也不需要把所有专业判断换算成一个效用总分。

0 层是分类的兜底。实际观察证据不足时，也可以报告 0，但必须同时报告信息不足的问题，不能据此断言对象在现实中完全没有进展。

## 4. 标量场怎样表达价值导向

这里的“价值”不是一般意义的好坏，而是人选择让工作推进的方向。

例如，对一个 Idea，导向可以是：整备工作条件，明确并确认目标，完成实现，最后让现实结果得到验证和接受。越高的层级表示越接近这一特定终局，不表示这个状态在所有人的所有价值维度上都更好。

ObjectiveGuide 负责解释当前层与下一层，ObjectiveRegulator 据此完成单目标
复测闭环：

```text
现在已经成立的条件是什么？
下一层还需要什么条件？
当前最先未成立的条件是什么？
应该给 Agent 哪种指导？
```

导向必须一致。如果规则要求 A 严格优于 B、B 严格优于 C、C 又严格优于 A，就无法用同一个全序标量场表达。这是导向的循环，不是我们希望建立的方法。

但执行中的循环是允许的：

```text
实现 -> 测试 -> 修复 -> 再测试
```

它可以始终服务于“实现通过验证”这一方向。Agent 行动之后，观察结果可能上升、保持或下降；标量场给的是意图，不是成功保证。

连续光滑模型中的标量势可以诱导无旋的梯度场。这里借用的是“方向与全局势一致”的直觉，而不是声称离散梯田可直接求出梯度，或仅凭层级数字就能算出具体行动。

## 5. 为什么需要观察副作用，而不只是纯分类函数

概念上可以讨论某个世界状态属于哪层，但程序不能暂停现实、取得完整瞬时状态再判定。

一次观察通常是一段采样过程：

```text
读取配置
查询运行时
检查仓库
获取远端事实
核对版本与决定
形成结论
```

因此 observation 是这段观察所支持的结论，不自动等于现实世界的一致性快照。观察期间现实仍可能变化；对版本和时效敏感的条件，需要专门核对。

每次新观察都重新判定，可以比上次低。观察内部可以共享采样结果，但不能把上一次的通过结论当作本次必然成立。

这也区分了两件事：世界状态在概念模型中有一个层级；程序是否有足够证据可靠识别它，是另一个问题。

## 6. 从判定到问题，再从问题到指导

层级判定不仅给出位置，也能在检查失败时产出“为什么尚未进入下一层”的诊断：

```text
观察对象
  -> 当前层级
  -> 阻塞问题：code + 具体说明
```

Code 负责连接可复用的专业经验，具体说明负责描述本次情况。只有证据支持的原因才能作为诊断；无法定位原因时，应报告需要进一步观察的问题，而不是猜测。

专业知识序列化为由平级页面组成的 Reference Wiki。页面可声明它处理的 code，
问题页面说明问题及首要处置方向，再通过内部链接引用其他知识页面；页面标签
开放，目录层级和预定义种类不决定语义。同一页面可以被多个问题共享，链接图
也不要求是无环树。Agent 收到问题时主动打开入口页面，再按需沿链接阅读或
搜索 Wiki；OG 不预先决定遍历深度或返回节点数量。未知 code 使用明确的知识
缺口页面，不能伪装成已知解法。

于是专业能力的积累分成两部分：

1. 如何观察、判定和区分问题；
2. 面对某类问题，怎样提供有用且受约束的指导。

Agent 根据这些信息决定一次具体行动。它可以主动查询 Wiki 并选择知识路径，
但不能为了宣称进展而自行降低判据；执行了某个页面描述的方法也不等于已升级，
仍需重新观察。

## 7. 为什么把检查看成子层

少量大层级方便专业人士理解自己的方法，但每层可能包含许多条件。例如设备整备可能需要运行时存在、版本兼容、相关入口可用。

把这些检查组织成层内逐关通过的子阶段，可以统一导航原则：

```text
大层级 0
  -> 子关卡 A
  -> 子关卡 B
  -> 大层级 1
  -> 子关卡 C
  -> 大层级 2
```

检查在首个未通过处停止，报告当前问题。大层级是对子关卡序列的压缩：对人保持简洁，对程序保留具体判据。

顺序是专业方法施加的求解秩序，不代表现实中的工作天然全序。它也不是唯一行动路径；不同解法可以满足同一关卡。代价是一次观察不列出所有潜在问题，因此最早需要处理的前置条件应排在前面。

## 8. 例子

### 8.1 Silvermoon：从 Idea 到现实结果

示意性的导向是：

```text
工作条件尚未整备
  -> 项目可开展工作
  -> Idea 已明确并接受
  -> 实现已完成并接受
  -> 部署结果已验证并接受
```

实际 `whats-next` 还要处理对象选择、仓库同步、schema、提交状态、控制权等，并非仅沿这份示意表机械执行。设备 readiness 中的非阻塞 advisory 也不能因这个类比而变成硬门槛。

若当前候选与已提交版本不同，问题应指出版本失效，指导应推动准备和提交准确候选，而不是直接让人接受旧版本。若控制权在人，下一步可以是交接和等待，不是继续改代码。

不同 Idea 共享生命周期骨架，但终局内容不同：密码重置能力上线，与构建耗时达到目标，属于不同对象上的价值导向实例。

### 8.2 采购：从需求到验收

可以定义如下层级：

```text
需求未明确
  -> 需求已明确
  -> 预算与权限已确认
  -> 采购已批准并执行
  -> 交付已验收
```

若阻塞问题是预算未确认，指导对应预算确认；若是交付不符，指导对应差异核查与处理。Agent 不需要提前知道所有供应商和异常的完整路径，但必须知道判据，且不能以“订单已下达”代替“交付已验收”。

这个例子说明候选应用方式，不构成本 Idea 对采购场景的实施或有效性承诺。

### 8.3 同一项目上的不同专业角色

架构师、PMO 和设计师可以在同一项目上定义不同标量场：

| 角色 | 终局示例 | 可诊断的问题示例 |
| --- | --- | --- |
| 架构师 | 系统满足约定架构原则与质量属性 | 职责边界不清、关键耦合未经处理 |
| PMO | 目标范围内的工作按约定完成 | 优先级冲突、依赖阻塞、进度风险 |
| 设计师 | 关键交互满足理解与体验标准 | 流程难理解、体验证据不足 |

一个项目可以在 PMO 导向下接近完成，却在设计师导向下仍待验证。这不是矛盾，因为投影的目的不同。

多个场不应自动相加成总分；各场的层级只是序数。Objective Portfolio
Supervisor 通过 portfolio policy 表达主导、门槛、资源、窗口与延后关系，
但不能篡改单个 ObjectiveGuide 的内部判据或把不同层级直接换算成总分。
本 Idea 只定义该协调边界和类型，不预写具体调度算法。

## 9. 从理论走向可迭代的专业能力

由此可以把方法论封装为：声明式层级与检查编排、可执行检查副作用、以问题
页面为入口的 Reference Wiki，以及公共装载和运行机制。

人和工具定义方向与判断标准，Agent 负责具体求解，新观察检验结果。失败反馈可以用于修正判据、问题分类或指导，不应一律归咎于执行者。

这是一种专业求解能力的通用建模候选，不是已证明适用于所有领域的万能算法。可靠采样、正确诊断和有效行动依然需要专业知识；目标也可能需要人工修订或放弃。

首轮验证已经在仓库内形成独立 module，并让 Silvermoon 的 `whats-next`
实际使用它，证明单目标观察与指导可以保留真实行为。下一轮先规范
ObjectiveGuide、ObjectiveRegulator 与 Objective Portfolio Supervisor 的
类型边界，再分别验证单目标循环与多目标监督；在取得这些证据前，不宣称跨
领域适用，也不以独立拆包或 npm 分发替代模型验证。
