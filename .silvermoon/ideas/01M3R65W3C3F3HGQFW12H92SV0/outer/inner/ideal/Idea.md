# 按开发、提交、CI 与发布场景分层验证

## 意图

让开发者与 Agent 在不同阶段运行与风险相匹配的检查集合，获得轻量、确定性的
日常反馈，同时保持提交、CI 和发布所需的完整保障。优化重点是验证策略与测试
归属，而不是无限增加进程并发或削减有效断言。

## 背景

`pnpm-check-regression` 已进行 fixture、耗时观测与测试文件拆分优化，但完整检查
仍包含真实 Git、打包安装、外部工具和网络相关工作。每轮编辑都运行全量验证，
既增加等待时间，也使反馈受网络与系统资源竞争影响。

当前 `check:quick` 运行全部 unit 与 contract，其中部分测试创建真实 Git 仓库、
执行命令或启动终端渲染；目录名称并不等于执行成本。`check:skills` 同时执行本地
副本校验与 `npx skills` 工具发现。普通 CI 已有平台矩阵和分层 job，但其检查集合、
本地推荐命令与发布工作流尚未形成明确一致的场景契约。

本 idea 与 `pnpm-check-regression` 独立，不替代其验收，不修改其状态，也不把创建
本 idea 视为对任何现有 revision 的批准或验收。

## 期望结果

### 明确的场景矩阵

以下命令为拟议的场景入口；实施契约应固化具体集合、兼容映射与证明方式。

| 场景 | 拟议入口 | 应承担的验证责任 |
| --- | --- | --- |
| 日常开发与 Agent 迭代 | `check:sanity` | 语法、纯逻辑与轻量 schema/契约；不运行真实 Git 子进程、终端集成、包安装或外部网络；改动相关的定向测试作为补充 |
| commit 前 | `check:commit` | sanity、本地文档/技能一致性及必要的真实 Git/CLI 冒烟；不默认执行 installed-package E2E 或远端发布验证 |
| PR 与 CI | 按职责拆分的 CI job | 完整 unit、contract、integration 与本地静态检查，保留现有平台与 Node.js 矩阵；按明确风险条件追加 package/E2E |
| 发布新版本前 | `check:release` 与发布工作流 | 全部发布级验证，并验证准备发布的实际产物；本地入口本身不发布包 |
| 发布后 | 现有发布验证入口 | registry 内容、完整性、provenance、README/CDN 等真实外部结果，不混入日常反馈 |

`pnpm check` 保持完整发布级验证入口的含义，不静默变成轻量检查。现有单套件入口
继续可独立运行；场景入口复用底层测试，不复制断言或制造多份漂移的覆盖清单。

### 正确性与可解释性

- 每个有效测试与门禁有明确归属；从轻量集合移出的检查必须在更高层执行，不能
  通过删除、扩大 skip 或弱化断言来提速。核心 CI 集合不因改动文件筛选而缩减。
- 昂贵 package/E2E 的条件必须覆盖包内容、依赖与锁文件、安装/CLI 入口、技能、
  测试基础设施、构建脚本及 workflow 等间接影响；无法判定影响或基线不可用时
  保守升级，不静默跳过。始终提供显式全量方式，发布前不得条件跳过必需验证。
- 将本地技能一致性与外部工具发现分开，外部依赖的失败明确报告，不伪装为成功。
- commit 前区分工作区测试和暂存快照校验。`silvermoon check --staged` 不能证明
  暂存代码已通过工作区测试；部分暂存时必须明确其限制，若承诺精确候选验证则
  需使用隔离的暂存快照，不能偷偷测试另一个候选。
- 分层后的失败诊断保留失败项与退出码；全量入口继续等待并汇总各门禁结果。
  日常入口不得因缺失工具、未知参数或错误选择而退化为空集合并成功退出。

### 可验证的反馈改善

实施前记录各场景当前对应入口的测试数量、外部 I/O、子进程及耗时，按同一机器、
checkout、Node.js/pnpm 版本执行一次预热和五次样本。依据基线在实施契约中预先
确定日常与提交层的改善目标，而非在实现后挑选有利数字。

通过确定性回归证明场景集合、覆盖守恒、风险升级、失败传播以及无网络的轻量
边界；性能数字只作同条件比较，不成为依赖绝对机器速度的普通 CI 硬预算。
记录完整样本和波动，不把缓存、网络或排队的偶然收益当成策略改进。

## 范围

### 范围内

- 按真实执行成本拆分混合测试文件：纯逻辑、本地契约、真实 Git/文件系统、
  终端集成、打包安装与外部发布验证；保留真实行为测试与隔离清理。
- 实现场景入口与共享调度，明确默认策略、完整模式和兼容入口。
- 对齐普通 CI、发布前验证、贡献者文档、Agent 指令与相关 workflow 契约测试。
  本地轻量入口不能与“每次改动都跑全量”的旧指令同时生效而失去意义。
- 为昂贵检查建立保守、可测试的触发规则与显式全量兜底；避免从不完整的
  依赖推断中产生漏测。
- 保持发布流程对不可变 revision 和实际待发布产物的身份、内容与安装行为验证。

### 范围外

- 删除现有有效验证、降低必需发布保障，或改变 `pnpm check` 的全量语义。
- 修改产品 CLI、schema、生命周期或人工决定语义来迎合测试。
- 全自动函数级受影响测试分析、远程测试缓存、常驻 daemon 或重量级测试平台。
- 未经授权安装强制 Git hook、修改全局 Git/系统资源设置或绕过分支保护。
- 运行实际 npm 发布或借此推进其他 idea 的批准、验收和部署状态。

## 约束

- 保持 Node.js `>=22`、Windows 与现有 CI 平台兼容；不牺牲当前平台矩阵换取速度。
- 不盲目提高并发；测试不得依赖文件执行顺序、共享可变状态或残留仓库、配置、
  引用、环境变量和后台进程。并发策略应考虑与其他门禁同时运行的资源竞争。
- 优先复用现有 runner、helper 和发布产物机制，不引入无必要的依赖或配置框架。
- 修改普通 CI 与发布流程时保留最小权限、受保护环境、不可变标签及正常非强制
  Git 同步；检查入口绝不隐含发布动作。
- 理想契约发布并获得明确批准前，只推进本 idea 的准备，不实现测试策略变更。
