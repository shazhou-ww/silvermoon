# 事件化状态、schema 升级与一次性迁移

## 意图

让 idea 的持久事实由 append-only JSONL 事件日志表达，以可重建的状态投影
取代可独立编辑的 `status.yaml`。即使没有 daemon 或真实 Agent，新模型也能
通过无状态 CLI 记录明确决策、观察当前生命周期并校验历史。

## 背景

本 idea 从
[设备级 daemon 总体设计](../../../../01M3SJ90WVJB56Z1PP72BPAHFZ/outer/inner/ideal/Idea.md)
拆出，单独承担持久化模型升级，而不同时引入交互协议和进程调度。

当前 `status.yaml` 保存生命周期事实；未来交互也需要可追加的持久记录。
统一事件事实和可重建投影，可以避免交接记录与可变 status 各自成为权威。
这里处理的是跨命令、跨进程保存的 idea 历史，不把现有单次 CLI 报告内的
命令事件流直接当作持久日志，也不保存全部运行输出。

## 期望结果

### 单一持久事实与确定性归约

每个 idea 在原 status 所在层级使用版本化 JSONL 保存事件，每行一个完整事件。
新 schema 下不再维护可独立编辑的权威 `status.yaml`；状态缓存如存在，
必须能完全从事件重建。事件元数据位于世界内容树之外，追加事实不会自行
改变被审查世界的 revision。

事件只保存重建状态所需的事实、必要结果和证据引用。idea 的身份、alias、
内容语言等仍适用的元数据必须有明确表示，不能在删除旧文件时静默丢失。
相同事件输入得到相同状态，不依赖 daemon 是否在线或某个 Agent 的会话。

### 人类决策绑定准确内容

批准、验收、放弃以及显式更正来自明确的人类决定，不从文字推测、执行完成、
Git 活动或沉默中推导。涉及世界版本的决策事件携带被决定对象的准确
revision/hash。

世界 revision 的变化或观察也进入归约所需的事件输入，使有效生命周期能由
事件重建。旧版本的批准事实保留，但不能自动适用于新版本。当前世界变化后，
CLI 必须观察并反映变化，不能无限沿用过期的“当前 revision”。

### 受控追加与历史检查

常规事件写入通过项目对应版本的 Silvermoon 子命令完成，由子命令校验并
追加，不要求 Agent 手工编辑 JSONL，也不能只交付库接口。
同一工作区的并发追加不得损坏记录或丢失已接受事实。

`check` 区分事件 schema、转换规则和历史 append-only 校验。相对于明确的
Git 历史基线，旧事件只能保留，不能删除、重写或静默重排；错误事实通过
追加显式更正表达。文件可以解析不代表其历史满足 append-only。

检查目标必须明确说明校验的是工作区、暂存区还是提交，以及相应历史基线。
缺少必要历史、未知事件、部分写入和无法解释的合并不得被静默跳过或冒充成功。
并发 Git 历史的校验和归约策略应保留双方事实，不依赖改写历史解决冲突。

### 独立的一次性迁移入口

选择升级的项目通过显式的一次性入口，将旧 `status.yaml` 中的已知事实导入
JSONL；成功切换后移除旧权威文件。入口独立于 Silvermoon 的常规主命令，
不是常规子命令，也不在普通启动时自动迁移。

迁移明确区分“导入既有事实”和升级后实际发生的事件，保留原有 idea 身份、
元数据及准确 revision。不能伪造未知的历史时间、操作者或事件顺序。
迁移失败后原始事实仍可恢复；安全重试不得生成重复决策或丢失事实。

### 不依赖 daemon 的验收边界

仅使用无状态 CLI 即可演示：旧状态显式迁移、准确 revision 的决策记录、
世界变化导致旧决定不再适用、事件回放重建相同状态，以及篡改既有事件被拒绝。
证明同时覆盖正常迁移、失败恢复、并发追加和历史检查，而非仅验证 JSONL
文件可以读取。

## 范围

### 范围内

- idea 持久事件 schema、身份与元数据表示、生命周期归约和 revision 观察。
- 替代 `status.yaml` 的读取和写入路径，以及校验并追加事件的 CLI 子命令。
- 相应 `check` 目标的快照、转换合法性与 append-only 历史检查。
- 独立的一次性旧格式迁移入口与失败恢复。
- 与新状态模型一致的无状态命令、文档、skill 及行为证明。

### 范围外

- `ping/pong` 的指令关联、调度状态转换与 Git 阻塞下的交互策略。
- daemon、Agent 适配器、session 管理和持续执行循环。
- 完整对话、工具调用、心跳等执行日志。
- 跨设备锁、中心协调服务或替代 Git primary 的事实权威。
- 自动批准、验收、发布 npm，或要求全部项目同步升级。

## 约束

- 本 idea 是总体方案的基础项，可独立实现和验收，不依赖后续 daemon。
- 本地交互协议会在该持久事件模型上增加交互事实和独立的调度投影；
  本 idea 不提前定义其轮次规则或要求所有事件都是生命周期决策。
- 整体交付目标仍为 `0.4.0` 和新的 schema 版本；前置 idea 的完成不各自
  触发 npm 发布，也不代表总体 daemon 已交付。
- 不把全部旧版本包是否支持新 schema 与设备 daemon 的版本绑定；
  本项只负责项目选择升级后的持久化行为。
- 保留未知修改与并发历史，不依赖 force-push、reset 或广泛 clean。
- 本次只记录契约，继续使用当前 schema 的 canonical 布局；各阶段决策独立，
  拆分本身不构成任何世界的批准或验收。

## 实施时需细化

JSONL 文件名、事件 envelope 与版本策略、元数据表示、revision 观察时机、
历史基线与合并规则，以及独立迁移入口形式由实施契约具体化。
这些细节不得改变“单一事实来源、准确 revision、显式迁移、只追加历史”的
产品边界。
