# 事件化状态、schema 升级与一次性迁移

## 意图

让 idea 的持久事实由 append-only JSONL 事件日志表达，以可重建的状态投影
取代可独立编辑的 `status.yaml`。即使没有 daemon 或真实 Agent，新模型也能
通过无状态 CLI 记录明确决策、观察当前生命周期并校验历史。

## 背景

本 idea 从
[设备级 daemon 总体设计](../../../../01M3SJ90WVJB56Z1PP72BPAHFZ/outer/inner/ideal/Idea.md)
拆出，单独承担持久化模型升级，而不同时引入交互协议和进程调度。

当前 `status.yaml` 保存生命周期事实；本项用确定性状态变更事件替代对
该文件的修改，不以未来交互需求为由引入不改变这份状态的持久事件。
这里处理的是跨命令、跨进程保存的 idea 历史，不把现有单次 CLI 报告内的
命令事件流直接当作持久日志，也不保存全部运行输出。

## 期望结果

### 单一持久事实与确定性归约

每个 idea 在原 status 所在层级使用版本化 JSONL 保存事件，每行一个完整事件。
新 schema 下不再维护可独立编辑的权威 `status.yaml`；状态缓存如存在，
必须能完全从事件重建。事件元数据位于世界内容树之外，追加事实不会自行
改变被审查世界的 revision。

事件只保存必要的业务状态变更及自增序，不附带审计或 Git 同步字段。
idea 的存在和身份由目录表达，空日志是合法初态；alias、内容语言等
仍适用的元数据用各自的更新事件表达，不能静默丢失。
相同 idea 身份与事件输入得到相同状态，不依赖 daemon 或 Agent 会话。

每个持久事件必须具备完成归约所需的全部信息，并实际改变原 `status.yaml`
表达的事实投影。仅观察世界、补充审计说明或重复设置相同值不构成事件；
不通过更新事件时间、序号或来源引用冒充业务状态变化。

### 人类决策绑定准确内容

批准、验收、放弃以及显式更正来自明确的人类决定，不从文字推测、执行完成、
Git 活动或沉默中推导。涉及世界版本的决策事件携带被决定对象的准确
revision/hash。

保留原 `status.yaml` 的状态推演逻辑：先从持久事件归约出当前有效事实，
再与本次实际观察到的三个世界 revision 比较。世界观察是本次状态推演的
显式输入，不是独立持久事件；只读查询不自动追加事件，也不新增“先将
观察持久化才能继续”的门槛。

旧版本的批准事实保留，但不能自动适用于新版本；不能扫描全部历史批准，
找到一个匹配值就视为当前批准。当前世界变化后，CLI 必须观察并反映变化，
不能无限沿用过期的“当前 revision”。仅回放日志时得到的是 status
对应的事实投影，不将它冒充为已经观察当前工作区的生命周期结论。

### 受控追加与历史检查

常规事件写入通过项目对应版本的 Silvermoon 子命令完成，由子命令校验并
追加，不要求 Agent 手工编辑 JSONL，也不能只交付库接口。
同一工作区的并发追加不得损坏记录或丢失已接受事实。每个 idea 使用连续
自增序号确定事件次序，不按时间排序；追加请求绑定已观察的前序版本。
前序变化时按乐观锁冲突处理，不能自动给旧请求换一个序号继续执行。

`check` 区分事件 schema、转换规则和历史 append-only 校验。相对于明确的
primary 历史基线，已提交并合入 primary 的事件只能保留，不能删除、
重写或重排；已集成的错误事实通过有效的追加更正表达。
尚未合入 primary 的本地候选可以在同步和重审后修改、去重、重新编号，
不把本地分支的旧候选 commit 当成不可修改的状态权威。
文件可以解析不代表其历史满足 append-only。

检查目标必须明确说明校验的是工作区、暂存区还是提交，以及相应历史基线。
缺少必要历史、未知事件、部分写入和无法解释的合并不得被静默跳过或冒充成功。
两个分支争用同一后续序号时，即使想写入相同状态，也必须先处理冲突。
`check` 拦截破坏 primary 前缀及事件序不合法的提交候选；
`whats-next` 和 skill 指引 Agent 保留现场、同步 primary，再基于新日志
重审本地改动。不同 idea 独立计数，不人为制造跨 idea 全局事件序。

### 独立的一次性迁移入口

选择升级的项目通过显式的一次性入口，将旧 `status.yaml` 中的已知事实导入
JSONL；成功切换后移除旧权威文件。入口独立于 Silvermoon 的常规主命令，
不是常规子命令，也不在普通启动时自动迁移。

迁移用普通状态变更事件重建已知字段，不引入 imported 类型；在格式切换
边界明确这些是既有事实，不是新的人工决定。保留原有 idea 身份、
元数据及准确 revision，固定归约顺序不声称还原历史发生顺序。
不向业务事件补造时间、操作者或 repo commit 依赖。
迁移失败后原始事实仍可恢复；安全重试不得生成重复决策或丢失事实。

### 不依赖 daemon 的验收边界

仅使用无状态 CLI 即可演示：旧状态显式迁移、准确 revision 的决策记录、
世界变化导致旧决定不再适用、事件回放重建相同状态，以及篡改既有事件被拒绝。
证明同时覆盖正常迁移、失败恢复、并发追加和历史检查，而非仅验证 JSONL
文件可以读取。

## 范围

### 范围内

- idea 持久状态变更事件 schema、身份与元数据表示、生命周期归约和只读 revision 观察。
- 替代 `status.yaml` 的读取和写入路径，以及校验并追加事件的 CLI 子命令。
- 相应 `check` 目标的快照、转换合法性与 append-only 历史检查。
- 独立的一次性旧格式迁移入口与失败恢复。
- 与新状态模型一致的无状态命令、文档、skill 及行为证明。

### 范围外

- `ping/pong` 的指令关联、调度状态转换与 Git 阻塞下的交互策略。
- daemon、Agent 适配器、session 管理和持续执行循环。
- 完整对话、工具调用、心跳等执行日志。
- 跨设备锁、中心协调服务或替代 Git primary 的事实权威。
- 自动批准、验收、发布 npm，或要求全部项目同步升级。

## 约束

- 本 idea 是总体方案的基础项，可独立实现和验收，不依赖后续 daemon。
- 本项不预留可任意追加交互记录的事件类型。下游若需要其他持久状态，
  须独立定义其状态及有效迭代边界；本项不提前定义 ping/pong 轮次规则。
- 整体交付目标仍为 `0.4.0` 和新的 schema 版本；前置 idea 的完成不各自
  触发 npm 发布，也不代表总体 daemon 已交付。
- 不把全部旧版本包是否支持新 schema 与设备 daemon 的版本绑定；
  本项只负责项目选择升级后的持久化行为。
- 保留未知修改与并发历史，不依赖 force-push、reset 或广泛 clean。
- 本次只记录契约，继续使用当前 schema 的 canonical 布局；各阶段决策独立，
  拆分本身不构成任何世界的批准或验收。

## 技术方案

[事件状态模型技术方案](./Technical-design.md) 是本 Ideal World 的配套
设计，随本世界 revision 一起审阅，不是第四份契约。它具体说明事件类型、
状态兼容性、观察与追加边界、并发与 Git 历史校验、schema 升级和迁移恢复。
[TypeScript 事件与归约模型](./Event-state-model.ts) 具体表达事件类型、
前后态转换及拒绝条件，同属理想设计，不是生产实现或迁移入口。

其中原状态推演、只读查询、持久事件必须改变状态，以及仅对已集成 primary
前缀强制 append-only 的边界已由用户明确确认。自增序与乐观锁的具体设计
及其他技术选择仍随准确 ideal revision 审阅，不代表已批准实施。
实施契约只在获批后细化模块、接口参数和执行步骤，不得改变这些边界。

业务模型遵循极简原则：非必要字段不加，状态归约与审计、写入校验、Git
同步和迁移机制分离；世界 revision 是业务对象，repo commit 不是事件参数。
