# 事件状态模型技术方案

本文服务于同目录的 [Idea.md](./Idea.md)，属于 Ideal World，不是独立契约。
当前是待审阅设计；事件名、文件名和命令面均描述拟交付行为，不表示当前
Silvermoon 已支持，也不授权本次迁移任何 idea。

用户已确认：原 `status.yaml` 的状态推演逻辑不变，只把修改状态事实改为
追加事件；查询实际世界时不自动写日志，也不等待一次额外的观察归档操作。
每个持久事件都必须确定性改变原 status 表达的事实，重复输入不追加无操作
事件。append-only 保护已提交并合入 primary 的前缀，不禁止同步后修改
尚未集成的本地候选。以下用 per-idea 自增序与乐观锁具体化这一方向，
其余技术选择仍随准确 ideal revision 一起审阅，不构成实施批准。

## T-01: 存储、版本与事实边界

新项目持久化格式采用 `version: 2`，每个 idea 的唯一持久状态事实入口为
根层级 `events.jsonl`，与 `ledger.md`、`outer/` 并列。新格式不保留
`status.yaml`，也不并行双写。三个世界的目录、canonical 文档和 Git tree
revision 算法不变；事件追加和 ledger 更新不改变世界 revision。

`events.jsonl` 使用 UTF-8、无 BOM、LF 分隔，每行一个完整的规范 JSON
对象，最后一行也必须以 LF 结束。空行、重复 JSON 字段、截断记录、重复
事件 ID 和未知字段均不合法。实现须固定序列化规则，不依赖不同工具
各自美化 JSON；Git 换行处理不得改变已记录事件的规范字节。

事件 envelope 使用 `schemaVersion: 2`，与项目新持久化格式一致。
它不是现有 `schema/v2/trace-event.schema.json` 的 trace 事件；相同版本号
不代表相同协议。事件 schema、项目格式、CLI 报告 schema 和 trace schema
分别明确自己的兼容范围，不把 `0.4.0` 包版本当作事件 schema。

持久日志只包含建立或改变身份/元数据/决策事实的状态迭代。
世界观察、来源说明和证据可以作为有效状态变更的上下文，但不独立成事件。
不记录命令启动/结束、完整对话、工具输出、心跳、调度或 `ping/pong`。
现有单次命令的 `intention / observation / actions / response` 和 trace
仍是独立输出，不能直接追加到 idea 日志。

缓存只可位于非权威本地位置，必须能删除后重建；命中条件至少包含完整
日志字节摘要、归约器版本和本次观察的世界 revision。缓存不能掩盖损坏、
未知事件、历史不足或并发冲突。

## T-02: 公共事件 envelope

每个持久事件的公共字段如下，具体 JSON Schema 在实施阶段落地。

| 字段 | 语义 |
| --- | --- |
| `schemaVersion` | 固定为支持的持久事件版本，本方案为 `2`。 |
| `eventId` | 唯一 canonical ULID，同时是一次追加的幂等键；不用于推断先后或发生时间。 |
| `ideaId` | 与所属目录一致的既有 idea ULID，不可通过后续事件改写。 |
| `type` | T-03 中的明确事件类型；不接受任意字符串扩展。 |
| `sequence` | idea 内从 `1` 开始的连续正整数；下一条恰为前一条加一，不重复、不跳号。 |
| `previousEventHash` | 前一条规范事件行的 SHA-256 摘要，不含分隔 LF；仅首条为 `null`。 |
| `basePrimaryCommit` | 形成该候选时已观察的准确 primary commit；不是含本事件的未来提交，避免自引用。 |
| `recordedAt` | 本次记录时间，使用 UTC RFC 3339；不充当原决定发生时间或冲突仲裁依据。 |
| `recordedBy` | 实际记录者的类别与已知身份；未知身份明确为空，不从 Git 作者猜测。 |
| `payload` | 该类型专属且严格校验的事实内容。 |

正常创建或迁移导入占用唯一的 `sequence: 1`；空日志的预期尾标识为
`sequence: 0` 和空 hash。使用可精确表示的整数，超出支持上限时报错，
不溢出、不循环。文件行序必须等于序号顺序；解析器不先排序再接受乱序文件。

不同 idea 独立计数。两个分支都从第 7 条出发，分别形成不同第 8 条，即使
两条都批准同一 revision，也存在同一日志位置的乐观锁冲突。
不按 `recordedAt`、ULID 或 Git 作者时间选赢家，不使用 DAG `parents`、
集合归并或为旧事件机械换号。准确恢复规则见 T-06/T-07。

尾序号用于判断位置，尾 hash 用于区分“序号相同但前序内容不同”。
事件链摘要和世界 Git tree OID 各有用途，不改变原有世界 revision 算法。
hash 链本身不能证明没重写整个日志，还必须检查已集成 primary 的字节前缀。

涉及人类决定的 payload 还记录 `decisionSource`：明确来自人类、已知的
决定者身份、可用的决定来源引用，以及确实知道时才记录的决定发生时间。
Agent 是记录者，不自动等于决定者；来源不明时不能伪装成人类刚作出的决定。
导入旧事实使用专门类型，不要求补造这些信息。

来源和证据只存必要引用，例如仓库相对路径与 commit、外部结果标识或
决定消息定位符；不嵌入完整执行日志、凭据或私有对话正文。引用不是指令，
CLI 不执行、插值或自动访问其内容。此模型不宣称提供人类身份认证或
不可伪造的数字签名；它约束结构、显式声明、准确对象和变更路径。

## T-03: 事件类型目录

### 每条事件必须是非空状态转换

持久归约的业务投影包含 `id`、可选 alias/language、可选 `abandoned: true`
以及三个批准/验收 revision，与旧 status 表达的事实对应。
`version` 是格式标记，不是可修改的业务字段；缺失可选字段仍按缺失表达，
不能将缺失、空字符串和 `false` 混为一谈。

每个事件以先前投影为前态，仅依靠已有事件和自身 payload 得到确定后态。
归约不能读取当前磁盘、网络、时钟、Git 作者或对话来补齐缺失事实。
除从未初始化到已初始化的首条事件外，后态必须与前态有实际字段差异。
序号、事件 ID、时间、记录者、来源/证据和用于更正定位的事实引用均不计入
这份业务差异，不能仅靠更新这些审计信息满足“状态改变”。

改变 alias 或批准 revision 是状态变化，即使五态标签没有变化也有效；
仅世界内容变化可能改变五态标签，但不改变 status 投影，不生成持久事件。
不增加 `state.changed`、纯观察或任意 `status.updated`/JSON Patch 后门。

保留原设计的 E-ID 方便审阅对照，撤销 E-04，不将它的 ID 挪给其他类型。
以下九种类型必须同时满足各自前置条件及共同的非空转换规则。

| ID | 事件类型 | 必需的业务输入与前置条件 | 对应的 status 迭代 |
| --- | --- | --- | --- |
| E-01 | `idea.created` | 尚未初始化；准确 idea ID、初始 alias/显式 language（如有） | 从无投影建立身份及元数据，无批准、验收或放弃。 |
| E-02 | `idea.imported` | 尚未初始化；完整已知 v1 状态及准确来源摘要 | 一次建立与旧状态等价的投影，不虚构旧决定序列。 |
| E-03 | `idea.metadata.updated` | alias/language 的明确设置或移除；每个被指定字段均实际改变 | 设置为给定值，或移除该字段；未指定字段保持不变。 |
| E-05 | `ideal.approved` | 准确 `idealRevision`，且不同于当前批准；明确决定及复核上下文 | 将 `approvedRevision` 设为给定 revision。 |
| E-06 | `implementation.accepted` | 准确 `implementationRevision`，且不同于当前验收；明确决定及复核上下文 | 将 `implementationAcceptedRevision` 设为给定 revision。 |
| E-07 | `deployment.accepted` | 准确 `deploymentRevision`，且不同于当前验收；明确决定及复核上下文 | 将 `deploymentAcceptedRevision` 设为给定 revision。 |
| E-08 | `idea.abandoned` | 当前未放弃；明确决定、原因及复核上下文 | 从缺失 `abandoned` 变为 `abandoned: true`。 |
| E-09 | `idea.resumed` | 当前已放弃；准确的有效放弃事实引用、明确撤销决定及复核上下文 | 移除 `abandoned`，不重新批准任何世界。 |
| E-10 | `decision.retracted` | 字段名、准确的当前决定引用及 revision；明确撤回决定、原因及复核上下文 | 移除指定的当前批准/验收字段；不恢复更早的值。 |

### 创建与导入

一个 idea 只能以 E-01 或 E-02 之一开始，不能两个都出现，也不能通过第二次
创建/导入重置历史。导入是在空的新格式投影上建立事实，不是伪装成旧事实
刚刚发生了变化。新建时的身份时间与已知实际创建事实可以记录；旧 idea
ULID 的时间部分仍可用于原有 inventory 时间筛选，但不能被冒充为旧决定的
发生时间。

E-02 将旧 `approvedRevision`、`implementationAcceptedRevision`、
`deploymentAcceptedRevision` 和 `abandoned` 表示为独立可引用的导入事实。
引用形式包含导入 `eventId` 和原字段名，使后续撤回可以准确指向某一事实，
而不是撤回整个导入事件、连带抹掉身份和其他决定。

### 元数据与不成事件的观察

E-03 的设置与移除必须区分：未提到的字段保持原值，显式移除 language
恢复动态继承；不得把当前用户或项目的 effective language 固化为 idea
override。alias 继续遵守格式与全项目唯一性规则。请求删除不存在的字段、
设置相同值或提供空更新都不追加事件；混合更新中的无变化字段须在明确的
预检结果中剔除后再形成请求，不悄悄把无效请求当成已执行。

撤销原 E-04 `worlds.observed`：它没有对应的 status 字段迭代。
一次世界观察仍完整包含同一快照的三个世界 tree、对象格式、目标种类和
已知的 commit/tree，供当前生命周期推演或有效决定的复核上下文使用。
它不能单独进入持久日志，也不能以“修正观察”为由追加审计事件。

### 决定、放弃与更正

E-05 至 E-07 必须绑定准确的世界 tree OID，而不是分支名、缩写 SHA、
“最新版本”或时间，并在对应的准备、实施或部署人工门槛记录。
复核上下文必须足以核对该门槛和被决定的准确世界；不能只给一个含义不明
的 hash，再要求归约器访问当前文件猜出决定对象。
E-08/E-09 是 idea 级决定，保留其发生时的准确世界
上下文，但放弃效力不因世界内容变化自动消失，保持原 `abandoned` 语义。

E-10 只撤回仍占据当前有效位置的批准/验收事实，字段名限于三个决定字段。
当前值、目标来源和预期 revision 必须全部匹配，否则拒绝该过期请求。
目标已被替代时不能只记录对旧事实的评论，因为这不会改变当前状态。
更早的同类决定不会因移除字段重新生效。
撤回放弃使用 E-09，不给两个类型制造相同但不同名的入口。

如果只是要把有效批准 A 改为经明确批准的 B，E-05 可直接完成该字段替换，
不强制制造一次中间撤回。确实撤销且尚无新批准时才用 E-10；不能通过
“先撤回再重批同一值”人为绕过无操作限制。已集成事件的审计说明可在
ledger 中补充，但不能借此改变 status 或清洗损坏历史。

## T-04: 兼容现有状态推演

归约先得到与旧 status 对应的事实投影：身份、可选 alias/language、
可选放弃事实，以及三个当前有效的批准/验收 revision。这只是内存投影，
不另写一个权威 status。再按原有顺序比较本次观察的世界：

| 优先级 | 条件 | 结果 |
| --- | --- | --- |
| 1 | 当前有效放弃事实存在 | `abandoned` |
| 2 | 当前有效理想批准不等于当前 `idealRevision` | `preparing` |
| 3 | 当前有效实施验收不等于当前 `implementationRevision` | `implementing` |
| 4 | 当前有效部署验收不等于当前 `deploymentRevision` | `deploying` |
| 5 | 三个世界的当前有效决定全部匹配 | `completed` |

缺少决定字段仍按不匹配处理。更改 ideal 仍通过嵌套 Git tree 使三个世界
revision 级联改变；事件没有引入另一套 hash 算法或额外生命周期阶段。
上游决定失效不删除下游历史验收，只通过原有优先顺序阻止继续。

对于合法的自增事件序列，同一字段使用最后一次有效写入，等价于原来修改
或移除该 status 字段，而不是按 revision 建立“永远有效的历史批准集合”。
例如批准 A 后改为 B，状态回到 `preparing`；若尚未批准 B 又将内容准确
还原为 A，保留的 A 批准重新匹配，和旧算法一致。若已批准 B 后再回到 A，
当前批准是 B，不能从历史中找回 A 来自动放行。

E-02 导入时，即使某个旧批准 hash 已不匹配当前世界，仍必须保留。
任意合法 v1 status 与相同世界观察，迁移后的事实投影及五态推演必须与
旧算法完全一致；不得以“清理过期事实”为由修改用户已经保存的状态。

## T-05: 只读观察与受控写入

### 查询保持只读

`whats-next`、`list-ideas` 和所有 `check` 目标继续不改工作区或 index。
原本允许的 fetch 行为保留，不因此变成持久事件写入。

查询先归约持久事件得到事实投影，再将本次真实世界快照作为显式输入，
按原算法推演生命周期。世界观察不是持久事件类型，不伪造 `eventId`，
不混入日志，也不以缓存中的“当前 revision”替代真实观察。

因此，已批准 A 而文件改成 B 时，查询直接报告 B 未批准；不要求先提交
一条观察事件。持久事件仍是所有可写状态事实的唯一来源，世界内容则仍是
原有 Git tree 的观察对象，不是第二份可独立编辑的 status。

纯日志回放得到 status 对应的事实投影，标出尾序号、尾 hash 和采用的日志；
没有显式世界快照时不输出声称代表当前世界的五态结论。
要复现某次生命周期结论，必须提供相同事实投影及相同世界观察。
决定事件里的旧审阅上下文不自动充当当前世界；实时查询标出实际快照。

### 拟交付命令面

常规 CLI 提供 `events` 命令组：`append` 校验并追加状态变更，
`revise` 在同步和显式重审后重新形成尚未集成的本地候选后缀，
`replay` 检查与回放持久事实。命令拼写可在实施契约中细化，但受控追加与
受控候选修订都必须可由项目版本 CLI 执行，不能只交付库接口。
取消原方案的 `events observe` 和自动归并日志的 `events merge`。

`append` 接受类型化业务请求、准确的 primary 基线和预期尾序号/hash，
验证前态、必需字段、非空转换及人类决定后，由 CLI 填充下一序号和
envelope。不能替调用者自动更新过期预期值，不能接收任意 JSON 行直写。
一条状态迭代包含其必需事实及决定上下文，无独立的“观察先写入”事务。

每次写入在首次尝试前固定 `eventId` 并提供给调用者。相同 ID、相同请求及
原记录仍存在时，重试返回原回执并标明未追加；相同 ID 配不同请求明确报错。
若回执遗失，重试也不能用当前新快照重写旧记录；回执须明确这是已记录的
原决定及其 revision，而不是声称新版本已获批准。

除可验证的原请求幂等重试外，换一个 ID 重复设置相同业务值也不能追加，
报告明确的 `no-state-change` 及当前事实来源，不输出“新事件写入成功”。
若请求使用旧前态，应先报告
乐观锁冲突，不能因为预期后态刚好与新状态相同就掩盖冲突；同步重审后
才可判断无需变更。手工塞进日志的无操作事件同样被 `check` 拒绝。

决定写入延续既有人工门槛：先同步候选到 primary，给出准确 revision 的
审阅索引，取得明确决定，再复核目标 idea、世界 hash 和观察到的 primary。
任何变化都返回冲突并要求重新观察，不改绑到最新内容，不自动重放决定。
如果仅 primary 的其他内容变化，重新观察仍要复核原授权对准确世界
revision 的适用性；世界或决定含义变化时重新取得人类决定。

写入报告明确区分本地候选已写入、已存在、无状态变化及失败；本地写入
不等于事件已集成 primary。失败必须说明是否写入及可复用的事件 ID；
仅命令运行成功或执行任务完成，绝不能转成批准/验收事件。
下游 Agent 根据回执处理 Git 同步，不把完整执行日志塞进本模型。

## T-06: 线性自增序、乐观锁与本地候选

同一 idea 的协作写入者使用工作区级的排他写入协议；持锁后重读日志、
验证请求的预期尾序号/hash、primary 基线和世界快照，再构造候选。
旧预期值即使指向同一序号但不同字节，也必须冲突，不覆盖他人的结果。
锁只避免同工作区物理写坏文件；逻辑并发由乐观锁和最终 primary 集成控制，
不跨设备加锁，也不把 Git 更新与文件写入假设为一个分布式事务。

普通 `append` 保留当前文件全部字节为前缀。`revise` 的特殊权限只涉及
已明确识别为尚未集成的候选后缀，必须保留最新 primary 的完整字节前缀，
不延伸到已集成记录。两者均可用同目录临时候选加原子替换保证读者只见
完整旧版本或新版本，不要求裸文件 append 系统调用承担事务。
回执在完整候选达到要求的持久化边界后才发出。

异常退出后的恢复依据可验证的原文件/候选摘要和事件 ID；不能仅凭锁的
年龄删除锁，不能把截断尾行当作成功，不能截断未知作者的记录。
外部编辑器或不遵守协议的 Git 操作不是协作写入者；检测到日志、index
或世界快照并发变化应停止，不能承诺用此锁阻止任意外部改写。
具体锁和原子替换实现需在 Windows、Linux、macOS 上证明。

### 已集成前缀与可修订后缀

不可改写的是已进入 primary 的事件序列；本地 Git commit 或候选写入回执
本身不构成集成。两个 Agent 各自在本地形成第 8 条时，先集成的一方成为
新的 primary 前缀，另一方不能把两条第 8 条都保留为有效持久事实。

后到者先保留本地改动与原请求上下文，refresh/sync primary，重新归约
最新日志，再重审自己的意图。若目标状态已达成，移除自己尚未集成的
重复候选；若仍需要且授权有效，基于新前态形成新候选事件；若意图过期、
已被替代或授权不再适用，则停止并明确需要重新决定的内容。

`revise` 接收重审后的类型化请求，而不是“将旧 JSONL 序号整体加一”。
用最新 primary 前缀重新构造候选后缀，并逐条验证确定性、非空状态迭代。
改变基线、序号或请求的候选使用新事件 ID，不把旧 ID 伪装为相同幂等请求。
废弃的本地候选不会作为“撤销候选”再写入业务日志。

此修订不要求删除或改写本地 Git 历史：可在本地形成普通后继提交或合并
结果；旧 commit 是候选形成过程，不是另一份已集成日志权威。
必须区分自己的候选与未知修改，不能自动丢弃其他 Agent/用户的记录。
当前文件损坏或含冲突标记时，仅能从准确的 Git 基础版本和已保留的候选
来源重建；无法确认来源和边界就阻塞，不提供任意覆盖坏日志的后门。

### whats-next 与 skill 的恢复责任

`whats-next` 在仓库/事件卫生阶段报告非 primary 前缀、序号冲突、
错误前序 hash 或过期基线，优先于生命周期继续指令。报告准确 primary
commit、候选尾标识和冲突位置，给出“保留现场、同步、重审、重新校验”的
顺序，不直接告诉 Agent 自动重排或把旧决定移到新 revision。

配套 skill 必须把该流程变成 Agent 行为：保留 selector/audience，同步
后读取新事实和世界，再通过项目 CLI 修订自己的候选；新序号由 CLI 产生。
Git 文本合并成功也不能跳过 `check`。修订后重跑检查，普通提交并尝试
非强制集成；primary 再移动就重新观察，不机械循环重试。

## T-07: 快照合法性与 Git append-only 历史

`check` 分别报告快照、转换/归约、历史三个结论；整体只有三者都通过才
退出 `0`。未知事件、损坏、冲突或必要历史不足均不得报告成功。
保留既有 `0` 通过、`1` 无效或不可用、`2` 用法错误的退出语义。

快照检查覆盖 schema、canonical 字节、唯一身份、完整世界、alias、
连续序号、前序 hash、完整类型输入、非空状态转换及实际世界的状态推演。
历史检查回答另外一个问题：相对于准确的已集成 primary 基线，是否真的
只增加了事实。仅重新计算 hash 链或改正 JSON 语法不能绕过前缀检查。
相同最终文件经不同历史形成，可以得到相同事实投影，但历史结论不同；
这正是相对于原来只检查 snapshot 的有意扩展。

| 检查目标 | 当前候选与已集成基线 |
| --- | --- |
| `--worktree` | 完整工作区候选对比固定 primary tip；本地 `HEAD` 只标识来源，不自动成为状态权威。 |
| `--staged` | index 候选对比固定 primary tip，不把未暂存内容当作已检查。 |
| 默认 / `--commit` | 未集成提交作为候选对比固定 primary tip；已集成主线提交按其当时的主线前驱审计。 |
| `--remote` | 固定本次 fetch 的 primary commit，审计其主线集成历史及当前快照，不借用本地候选。 |

本地检查保持不自动 fetch，使用已经观察并固定的 primary commit，输出
该基线与来源；不能把过期 remote-tracking ref 称为“最新远端”。
基线选择必须能验证其配置的 primary 身份，不能随便用某个祖先或共同
merge-base 来绕过 primary 已接受的后续事件。必要基线不可用就明确失败。
集成前必须刷新 primary 并重新检查；此前检查不证明移动后的 tip 仍适用。

每个结果暴露精确候选 tree/commit、primary 基线、候选/已集成角色、
审计边界和缺失对象。沿 primary 集成主线验证已有日志的字节前缀，
不能只比较最后一次提交而漏掉更早的篡改。缓存绑定已验证 commit/blob、
基线和校验版本；根初始化或显式 v1 迁移是边界，shallow 缺失父对象不是。

候选必须以对应 primary 日志的完整字节为前缀，后缀从下一序号连续追加，
每条 hash 和状态前置条件均成立。缺失旧 idea、删除/改名日志、重置身份、
改写旧行、插入中间、重复/跳号/倒序及追加无操作事件都不合法。
新增 idea 走唯一合法起点，不允许删除再创建来逃避历史。

### 合并结果校验，而非保留所有候选事件

合并结果以被更新的准确 primary tip 为乐观锁基线，不要求以每个本地
父提交的日志为前缀，也不把各分支曾经提交的候选自动提升为不可删事实。
此前“保留所有父日志、按相对顺序求并集”的设计撤销。
两条竞争的第 8 条即使业务后态相同也不能直接合并；必须完成 T-06 重审，
最终只保留 primary 的第 8 条，再追加仍然需要且合法的第 9 条等。

Git 的 conflict 只是提示，不是完整校验器；没有文本冲突也可能违反事件序。
`check --staged` 校验实际拟提交结果，集成侧检查校验实际拟进入 primary
的 commit 和准确旧 tip；两侧都不能用检查过某个分支旧快照冒充结果。
旧 tip 在检查后移动时，普通非强制更新不得覆盖新历史，应同步重审。

为了在 Git 中可重建“已集成”边界，集成提交以原 primary 为 first parent，
本地候选形成过程位于其他父链。primary first-parent 主线上的每一步都
必须 append-only；其他父链用于保留形成过程，不要求其旧候选不可修改。
若某个本地分支曾撤换候选、其历史不能逐步满足该规则，就不能将整段
历史 fast-forward 成 primary 主线；应形成以当前 primary 为 first parent
的普通合并结果，保留本地历史而不 reset、rebase 或 force-push。
合法的直接提交或整段均满足规则的 fast-forward 仍可使用，不强制每次
同步都制造合并提交。

校验必须绑定实际被更新的 primary 和预期旧 tip，不能任由提交者挑一个
有利的 first parent 来掩盖之前已集成的内容。这是本项需要落地的 Git/CI
集成约束；仅运行一次本地 `check` 不能阻止外部工具绕开检查去 push。
skill 和仓库门禁需明确采用该校验，不能宣称 CLI 是不可绕过的服务器锁。

这里验证的是可见 Git 历史上的相对完整性，不是密码学意义上抵御整库历史
被替换的证明；仍依赖普通非强制 Git 和 primary 保护。损坏的已提交历史
或无法解释的合并必须报告具体阻塞，不承诺用一次“修复事件”绕过它。
已集成的坏记录不能以“当时是本地候选”为由事后删除。
旧版导入中不可考证的决定 hash 与缺少必要 primary 审计历史是不同问题：
前者按来源保留，后者不能放行。

## T-08: 独立迁移与恢复

提供随对应包版本分发的独立一次性入口 `bin/migrate-v1-to-v2.js`，不注册
成 `silvermoon migrate`，不由普通启动、安装、查询或 daemon 自动调用。
入口提供预检计划、显式应用、恢复和未完成事务的回滚路径；它不自动
commit、push、批准、验收或发布。

升级以单个项目为单位：所有既有 idea（包括 completed/abandoned）与项目
格式标记一起切换，不能留下部分 v1、部分 v2 由运行时自行猜测。
新运行时仍能识别并读取未升级项目和迁移前历史；普通新格式事件写入不对
v1 项目偷偷生效。对新 schema 的不支持必须明确报错，不能当成空项目。

预检记录固定来源 commit、项目配置和每个 status 的原始字节摘要/可用
Git blob OID、idea 集合及世界快照。开始应用前重验全部来源，存在未知
改动、冲突、已有不明日志或来源移动就停止；不覆盖、不合并猜测。

每个旧 idea 生成一个 `sequence: 1` 的 E-02，完整保留 `id`、alias、显式 language、
放弃和三个 revision 字段，保留“缺失”与“有值”的区别。
世界、ledger 和已有证据原样保留。导入记录时间是迁移时间，原决定的
未知时间、操作者、顺序明确未知；不把字段排列顺序伪装成历史发生顺序。

迁移计划在应用前固定各导入事件 ID 和原始来源摘要。临时备份与恢复日志
是未完成迁移的非权威材料，不是另一套长期 status。安全重试复用同一
计划；已经导入且来源一致的 idea 不追加第二个导入或重复决定。
来源不同、事件不一致时报告冲突，不靠“再跑一次”覆盖。

多文件切换采用可恢复事务，而不假设跨文件原子写。先准备全部候选并验证
v1/v2 投影等价，再执行切换、移除旧权威文件和更新项目格式。
事务未完成时，新运行时明确识别待恢复/混合格式并拒绝正常操作；恢复入口
可完成原计划或在尚未接受新事件前还原原始文件。
旧工具必须因格式/布局不兼容而失败，不可在半迁移项目上继续写旧 status。

只有完整切换且验证成功才报告完成；最终集成提交必须包含完整的一次 schema
迁移边界。历史检查在该边界核对 E-02 与 primary 前态的旧事实一一对应，之后
按新格式 append-only 规则继续。不能对非空新日志重新执行迁移来覆盖它；
完成迁移并追加新事实后，不支持回滚成会丢失这些事实的旧格式。

## T-09: 可观察的行为证明

下面是实施时必须转成自动化用例及无 daemon 演示的设计判据，不是已执行
结果。I-S/I-AC 和 D-S/D-AC 仍在各自生命周期阶段制定。

| 场景 | 必须证明的结果 |
| --- | --- |
| v1 全部合法字段组合与五态 | 同一世界观察下，导入前后事实和值完全一致，推演结果与旧算法一致。 |
| 批准 A 后改为 B | 只读查询立即回到 `preparing`，日志不变，不要求先记录 B。 |
| 精确还原内容 | 未替换的 A 批准可重新匹配 A；已被 B 替换的 A 批准不会从历史自动复活。 |
| 世界嵌套变化 | ideal、inner、outer 的原级联失效规则保持，事件追加本身不改变三者 hash。 |
| 每种事件的非空转换 | 必需字段不足时失败；完整输入独立完成确定性归约；审计字段改变不算业务状态变化。 |
| 无操作请求 | 重复元数据/批准/放弃、删除缺失字段、撤回过期决定和纯观察均不追加；手工追加也被检查拒绝。 |
| 更正与放弃撤销 | 仅撤回准确当前事实，保留已集成旧记录；不恢复旧批准，不清除后续决定。 |
| 过期决定请求 | 审阅后 primary 或目标世界改变，拒绝旧请求，不改绑、不自动批准。 |
| 同工作区并发与崩溃 | 旧尾预期冲突且不自动换号；候选写入完整，失败/重试可判明结果，不吞截断行。 |
| 幂等重试 | 同 ID 同请求返回原回执；不同请求复用 ID 报错，不能静默当作成功。 |
| 两 Agent 同序竞争 | 无论写相同值还是不同字段都先冲突；后到者同步并重审，不归并两条同序事件。 |
| 基于新 primary 修订 | 只替换自己未集成的后缀；重复候选可删除，仍需变更才形成新 ID/序号，不改 primary 前缀。 |
| 本地历史边界 | 修订可形成普通后继/合并提交，不要求重写分支历史；集成检查不把旧候选当已接受前缀。 |
| append-only 审计 | primary 旧行删除/改写/重排、删 idea、跳号/重复/倒序和错前序 hash 均失败。 |
| 集成基线竞争 | 检查后 primary 移动不能覆盖新前缀；过期本地通过结果不被当成新 tip 的证明。 |
| 不完整或损坏历史 | 必需主线历史缺失、未知事件、重复 ID、截断和冲突标记均明确失败。 |
| 检查目标隔离 | 工作区、index、commit、remote 的候选和基线准确可见，不互相冒充证据。 |
| 回放与缓存 | 相同持久输入得到相同历史投影；相同输入加相同实时观察得到相同当前状态，删缓存不改结果。 |
| 迁移故障注入 | 任一切换阶段中断可恢复原事实或完成同一计划；重试不新增重复决定，未知来源不被改写。 |
| 元数据继承 | alias/identity 保留，缺失 language 仍动态继承，不伪造旧时间、作者或先后。 |

## T-10: 审阅重点与实施留白

本方案需要审阅的选择是：九种确定性状态迭代、撤销纯观察 E-04、
自增序与前序 hash、primary 乐观锁、受控本地后缀修订、可审计的集成主线，
以及项目级可恢复迁移。它们不是十种事件加 DAG 自动合并方案的增补，
而是根据用户反馈对该方案的替换。

实施阶段可以选择具体的模块划分、CLI 参数拼写、JSON 字段完整 schema、
锁/持久化实现、缓存策略和测试组织，但不得借此改成查询自动写入、
历史批准集合自动匹配、审计信息冒充状态变化、按时间/集合归并事件、
以本地旧候选限制修订、自动迁移或无校验直接追加。
若实现验证发现上述关键选择无法可靠满足，回到 Ideal World 修订并重新
审阅，不由实施阶段静默改变语义。

本项的事件只能改变上述 status 事实投影，不为 local-agent-handoff 预留
不改变此状态的交互/审计事件。下游若需要其他持久状态，必须先独立定义
其状态与有效迭代契约，不能把任意消息直接塞入本日志。
当前运行时对未知事件失败关闭。本项不定义 ping/pong、Agent session、
daemon 调度和 Copilot 适配，亦不授权 npm 发布。
