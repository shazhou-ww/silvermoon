# 事件状态模型技术方案

本文及 [Event-state-model.ts](./Event-state-model.ts) 服务于
[Idea.md](./Idea.md)，是待审阅的 Ideal World 设计，不是生产实现或迁移授权。

## T-01: 最小业务模型

事件只表达旧 `status.yaml` 业务字段的确定性变化。不为审计、未来扩展、
Git 同步或缓存方便而增加业务字段。职责分开：

| 层次 | 责任 |
| --- | --- |
| idea 布局 | 目录确定身份和存在；不需要 created 事件。 |
| 持久事件 | 记录非空状态转换及其顺序。 |
| reducer | 从初态与事件纯计算 status 对应的事实投影。 |
| 生命周期推演 | 用事实投影与显式传入的当前世界 revision 按旧算法比较。 |
| 写入命令 | 验证输入、人工授权、准确世界与并发前态，生成候选日志。 |
| Git/check | 校验已集成 primary 前缀、候选顺序及合法性。 |
| 一次性迁移 | 从旧事实生成普通事件，负责迁移来源校验、备份和恢复。 |

业务事件不携带 repo commit、操作者、时间、观察快照或决定消息定位符。
人类批准绑定的世界 tree OID 是必要业务值；repo commit 只是外层同步依据，
不能使一个 idea 的局部状态转换依赖整个仓库的 commit。
业务上没有参数的事件不放空 payload。

## T-02: 存储与序号

新项目持久化格式采用项目级 `version: 2`，每个 idea 根目录以
`events.jsonl` 替代 `status.yaml`，与 `ledger.md` 和 `outer/` 并列。
身份由 canonical ULID 目录确定，不在每条事件重复存储。
空文件是合法日志，对应只有身份、其他字段缺失的初态。
文件缺失则是布局错误，不能当作空日志悄悄恢复状态。

每行一个规范 JSON 对象，UTF-8、无 BOM、LF 分隔，非空文件末行也以 LF
结束。重复 JSON 字段、未知字段/类型、空行、截断、冲突标记均拒绝。
序列化规则固定，Git 换行处理不得改写已集成前缀。

每条事件只含 `sequence`、`type` 和该类型需要的 `payload`。
`sequence` 是 idea 内从 1 开始的连续安全整数，文件顺序就是事件顺序。
不按时间、ULID 或 Git commit 排序，不接受重复、跳号、倒序，不先排序再校验。
超出支持的整数范围必须报错。不同 idea 独立计数。

删除原方案的 Envelope，包括 `eventId`、`ideaId`、逐行 `schemaVersion`、
`previousEventHash`、`basePrimaryCommit`、`recordedAt` 和 `recordedBy`。
项目格式选择严格 schema；后续不支持的格式/事件必须明确失败。
乐观锁仍需要比较准确前态，但日志摘要在写入请求中计算和比较，不嵌进事件。

## T-03: 七种状态变更

[TypeScript 模型](./Event-state-model.ts) 直接列出显式 discriminated union，
每个分支的 type 和 payload 并列，避免映射类型造成审阅间接性。

| 事件 | 必要参数 | status 对应迭代 |
| --- | --- | --- |
| `alias.updated` | `alias: string \| null` | 设置 alias；null 移除该字段。 |
| `language.updated` | `language: string \| null` | 设置显式 language；null 恢复继承。 |
| `ideal.approved` | `idealRevision` | 设置 `approvedRevision`。 |
| `implementation.accepted` | `implementationRevision` | 设置 `implementationAcceptedRevision`。 |
| `deployment.accepted` | `deploymentRevision` | 设置 `deploymentAcceptedRevision`。 |
| `idea.abandoned` | 无 | 设置 `abandoned: true`。 |
| `idea.resumed` | 无 | 移除 `abandoned`。 |

无 `idea.created`：存在已隐含创建；alias/language 用各自更新事件表达。
无 `idea.imported`：迁移使用相同普通事件，不让迁移机制污染日常模型。
无通用 metadata patch：两种元数据独立更新，顺序归约的代价可忽略。
无 `worlds.observed`：观察不改变 status 事实，不能独立持久化。
无 `decision.retracted`：本项不引入内容不变时单独清空批准/验收的能力。
无审计补充、执行完成或生命周期标签变更事件。

同值设置、清除缺失字段、重复放弃/恢复均为无操作，拒绝追加。
只有审计信息不同也不构成状态变化。批准/验收字段只能通过明确决定设置
为准确世界 revision，不能通过 null、通用更新或替代事件清空。

## T-04: 纯 reducer 与旧五态

`initialEventState(ideaId)` 从目录身份建立 `{ status: { id }, sequence: 0 }`。
`reduceEvent(before, event)` 校验连续序号、类型转换和非空业务差异，
不修改输入；失败返回明确错误，不消费序号。
`replayEvents(ideaId, events)` 按原文件顺序执行，首个错误即停止。
内部 sequence 是遍历游标，不作为“业务状态变化”的依据。

reducer 的输入已通过严格 schema 解析。`string` 类型别名不替代 ULID、
Git OID、alias、BCP 47 等运行时验证；未知字段及不合法值由外层拒绝。
模型不是接受任意 JSON 后强行断言类型的捷径。

`deriveLifecycle(status, worlds)` 保留现有顺序：

1. abandoned 存在则为 `abandoned`。
2. 当前理想批准与 ideal revision 不同则为 `preparing`。
3. 当前实施验收与 implementation revision 不同则为 `implementing`。
4. 当前部署验收与 deployment revision 不同则为 `deploying`。
5. 否则为 `completed`。

更改 alias 是有效状态变更，即使五态标签没变。世界内容变化可能改变
五态标签，但不是 status 事实变更。只读查询仍观察真实世界，不写日志。
纯回放只得到事实投影；没有传入世界 revision 就不能声称给出了当前五态。

同字段使用最后一次有效写入，不扫描全部历史找匹配批准。
批准 A 后改为 B，旧批准不适用于 B；未批准 B 又精确还原 A，原 A 批准
重新匹配。若已经批准 B，再还原 A，不能从历史复活 A 的旧批准。
上游失效不删除下游验收事实。

需求、方案或结果改变时，修改对应世界的实际内容，让嵌套 tree revision
自然使本层及下游旧决定不再匹配，再按阶段审阅。不为重置而制造无意义
内容变化。仅清空上游批准再批准同一 revision，可能让旧下游验收直接
重新匹配；本项不提供这种独立撤回/重置能力。
放弃及显式恢复仍保留既有语义，不借它们清除批准或强制重新验收。

正常决定写入的人类门槛与世界复核属于命令层，而不是纯事实 reducer。
否则既有的过期批准或不完整验收组合无法按原值迁移重建。
事件不包含授权凭证，也不宣称通过 JSON 结构就能证明真实人类授权。

## T-05: 写入命令与幂等

项目版本 CLI 必须提供受控追加、未集成候选修订和回放能力，不能只交付库，
也不要求 Agent 手工拼接 JSONL。具体命令参数在实施契约中细化。

写入请求包含目标 idea、业务请求、预期日志长度/序号及整个日志的摘要。
持锁后重读并核对准确前态；序号相同但字节不同仍是冲突。
先判断前态是否过期，再判断新状态是否为无操作，不用“现在值刚好相同”
掩盖过期请求。序号由 CLI 根据核验后的前态产生，不自动给旧请求换号。

写入前完成格式验证、全项目 alias 唯一性检查以及适用的人工门槛复核。
批准/验收针对准确世界 revision，在候选同步 primary 并获得明确人类决定
后记录。恢复、放弃同样要求明确决定。
primary 变化时重新观察，世界或授权含义变化时重新取得决定，不能静默重放。
primary commit 只出现在外层观察、检查结果或命令上下文，不写进业务事件。

回执区分“本地候选已写入”“原追加已存在”“无状态变化”“冲突/失败”，
不把本地写入称为已集成 primary。失败说明是否已写入和恢复所需前态。
无需独立 eventId：以原日志前缀摘要、预期追加位置及规范业务事件确认
重试是否已经写入相同记录。无法确认原前缀或记录已被本地修订替换时
报告冲突，不拿新前态再次执行旧请求。
换一个请求重复写相同状态也不会生成新事件。

一次 alias 加 language 修改自然是两个事件，不承诺跨事件原子性。
若第二条失败，明确第一条已成功，重试时读取新前态，不能把半完成称为全部成功。

## T-06: 并发与可修订候选

同工作区排他写入协议避免物理记录损坏，预期前态比较负责逻辑乐观锁。
原子替换文件时普通追加保留全部当前字节；读者只见完整旧版或新版。
回执须在要求的持久化边界后发出。异常恢复依据准确候选/原文件摘要，
不凭锁年龄删除锁，不吞截断行，不截断未知作者记录。
Windows/Linux/macOS 的锁和替换细节由实施证明，不假设跨设备锁。

不可修改的是已提交并合入 primary 的前缀。本地 commit 只是候选形成过程，
未集成后缀允许在同步和重审后调整、去重、重新编号。
两个 Agent 都从第 7 条形成不同第 8 条，即使业务值相同也先发生冲突。
先集成的一方成为前缀，另一方必须保留现场、同步、重新归约和重审意图。
状态已达成则删掉自己的重复候选；仍需且授权有效才生成后续新事件。

修订能力只重建明确属于自己的未集成后缀，不修改 primary 前缀，不机械
给旧序号加一，不自动丢弃未知修改。无法确认来源或边界就阻塞。
普通后继或合并提交可保存修订结果，无需改写本地 Git 历史。

`whats-next` 在卫生阶段明确报告非追加、乱序、过期前态，优先于生命周期
继续指令。skill 指引保留 selector/audience，先同步、重审，再通过 CLI
修订候选、检查并普通提交。Git 没有文本冲突也不能跳过事件检查。

## T-07: check 与 primary 历史

分别报告快照、转换和历史结论；只有全部通过才退出 0，无效/不可用为 1，
用法错误为 2。不能用可解析或一次局部回放替代历史合法性。

| 目标 | 候选与基线 |
| --- | --- |
| worktree | 完整工作区候选对比已固定 primary tip。 |
| staged | index 候选对比已固定 primary tip，不包含未暂存内容。 |
| HEAD/commit | 未集成候选对比固定 primary；已集成主线提交按当时主线前驱审计。 |
| remote | fetch 后固定 primary tip，审计快照和主线集成历史。 |

本地检查不自动 fetch，明确报告基线来源，不把旧 tracking ref 称为最新远端。
集成前刷新并固定实际被更新的 primary，校验其完整字节前缀及新增后缀：
连续序号、严格 schema、每条非空转换。删除旧 idea、改写/删除/重排旧行、
重复/跳号、无操作、未知类型、损坏和必要历史缺失均不得放行。
空日志合法不意味着允许把已集成非空日志清空。

沿 primary first-parent 集成主线检查到初始化/迁移边界，不能只查最后
一个 commit 漏掉此前篡改。shallow 缺父不是新根。
本地其他父链的旧候选不要求永久保留为日志前缀；最终合并结果才是候选。
包含候选撤换的分支不能直接 fast-forward 成不合法主线；应保留本地历史，
形成以当前 primary 为 first parent 的普通合并结果。
直接提交或每一步都合法的 fast-forward 仍可采用。

集成侧检查必须绑定实际 primary 及准确旧 tip，不允许任意挑有利基线。
检查后 primary 移动则重新观察，不能依赖旧通过结果覆盖新前缀。
CLI 不是不可绕过的服务器锁，仓库门禁需采用相同检查；
禁止 force-push/reset/广泛 clean，不能用“修复事件”洗掉损坏的主线历史。

## T-08: 独立的一次性迁移

独立入口 `bin/migrate-v1-to-v2.js` 随对应版本分发，不注册为常规子命令，
不在启动、安装、查询或 daemon 自动执行，不自动 commit/push/批准/发布。
升级以整个项目为单位，所有 idea 与格式标记一起切换，不留下混合格式。

旧状态从目录身份初态重建。迁移工具只对存在的字段，按固定顺序生成
alias.updated、language.updated、ideal.approved、implementation.accepted、
deployment.accepted、idea.abandoned，序号从 1 连续分配；没有字段就生成
空日志。完整保留已知值和缺失，包括不再匹配当前世界的旧决定。

这个固定顺序是新表示的归约顺序，不是对过去发生顺序的声明。
普通事件在迁移边界表示既有事实，不表示重新作出决定；迁移过程无需
假装通过今天的人工门槛，也不补造未知时间、操作者或批准历史。
之后正常追加仍执行现有人工门槛。身份、world、ledger、证据原样保留。

迁移来源、旧原始字节摘要、固定计划和备份属于迁移工具，不进入业务事件。
先校验全部来源，准备所有日志并证明投影等价，再可恢复地切换文件与
项目格式，成功后移除旧权威 status。未完成事务明确阻塞正常操作，
恢复可以完成原计划或在未接受新事实前还原原始文件。

固定来源与计划使输出确定；重试识别已完成的同一转换，不重复追加。
来源变化、未知日志、冲突或计划不一致就失败，不覆盖猜测。
最终集成以迁移前 primary 事实逐项核对普通事件重建结果，将该提交标识
为历史上的格式迁移边界；无需 imported 事件或行内来源字段。
已经完成迁移且接受新事实后，不能回退为会丢失新事实的旧格式。

## T-09: 行为证明

以下是实施判据，不是当前功能已实现的声明：

- 每个事件只有必要字段；缺字段/未知字段/无操作均失败，纯 reducer 不做 I/O。
- 空日志从目录身份得到初态；alias/language 分别设置和清除，保持动态继承。
- 旧合法字段组合迁移后逐项相等，并与旧算法推演出相同五态。
- 查询世界变化不写事件；准确还原与替换后的批准行为符合旧逻辑。
- 不支持清空批准/验收；修改 ideal、inner、outer 时分别保持原有级联失效范围。
- 同序竞争、同序不同前缀、重复请求、第二条失败和崩溃均能明确判别结果。
- 本地修订保留 primary 前缀；主线篡改、非法序号、缺历史及损坏均失败。
- 迁移任一步中断可恢复，重试不重复；没有字段时迁移为空日志仍有效。
- 同一身份与事件输入得到相同投影；加上同一世界观察得到相同五态。

## T-10: 审阅与后续边界

业务模型采用用户要求的极简原则，删除旧方案中的 created/imported、
metadata patch、审计 envelope、来源索引及持久观察。
同时删除独立的 decision.retracted；业务变化通过修改对应世界内容驱动
重新审阅，不新增清空决定的替代入口。
TS 模型只表达字段迭代、自增序和旧五态；严格 schema、物理写入、Git 门禁、
授权和迁移恢复在各自边界实施，不向业务事件反向添加工具层字段。

仍需在实施契约中细化规范 JSON、命令参数、写入/恢复协议和门禁接入。
若发现必须改变业务契约，先回到 Ideal World 审阅，不静默扩大字段或类型。
不预留不改变 status 的交互事件，不实现 ping/pong、daemon、Agent session
或 Copilot 适配，不授权 npm 发布。
