# 加快测试反馈

## Intent

显著缩短 Silvermoon 完整测试检查的等待时间，让开发者和 CI 更快获得可信反馈，同时保持现有行为覆盖、测试隔离与发布门禁强度。

## Context

当前测试分为 unit、contract、integration 和 e2e 多个层级，完整的 `pnpm check` 还包含 Markdown、打包与 skill 检查。集成测试会为许多用例重复创建临时 Git 仓库和 bare remote，并执行 init、commit、fetch、push 等同步子进程；这些真实仓库行为对正确性很重要，但也可能形成主要耗时。仓库目前缺少可重复的分层基线和性能回归判据，因此无法可靠判断优化是否真正改善了常用反馈路径。

## Desired outcome

在相同机器、Node.js/pnpm 版本和提交内容下，以至少五次预热后运行的中位数比较，`pnpm check` 的端到端耗时相对实施前基线降低至少 30%。`pnpm test`、`pnpm test:integration` 和 `pnpm test:e2e` 的分层耗时可被单独观察，所有既有测试、包内容检查、文档检查和 skill 检查仍通过，且测试结果不依赖执行顺序、共享可变状态或外部网络。

## Scope

### In scope

- 建立可重复的完整与分层测试耗时基线，定位时间主要消耗在哪些套件、fixture 和外部进程。
- 优化测试 fixture、Git 仓库准备、进程调用、文件系统工作和安全的并行执行。
- 在不降低断言与行为覆盖的前提下，消除重复准备工作和不必要的跨进程开销。
- 为本地和 CI 提供清晰的快速反馈入口，并记录完整发布级检查的使用方式。
- 增加轻量、稳定的性能回归证据，使后续改动能够发现明显的测试速度退化。

### Out of scope

- 通过跳过、删除或弱化现有测试和发布门禁来换取速度。
- 改变 Silvermoon 的用户可见 CLI、协议、schema 或 idea 生命周期语义。
- 依赖特定开发者机器的绝对毫秒阈值，或引入持续运行的外部基准服务。
- 优化生产代码运行性能，除非该改动仅移除测试专用的重复开销且不改变生产行为。

## Constraints

- 性能比较必须在一致环境中采用多次运行的中位数，避免以单次波动宣称改进。
- 临时目录、Git 配置、环境变量和测试替身不得在用例间泄漏；支持单文件、分层和完整套件独立运行。
- 涉及真实文件系统和 Git 行为的契约仍须由 integration/e2e 测试证明，不得全部替换为 mock。
- 保持 Node.js `>=22`、Windows 与现有 CI 平台兼容，不新增仅为基准所需的重量级依赖。
- `pnpm check` 仍是发布级完整验证入口，失败必须保持显式且可诊断。
